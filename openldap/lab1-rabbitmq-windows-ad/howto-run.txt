1. 测试基础认证与 Bind（验证密码是否正确）
最常用命令，直接测试某个账号和密码能否连接 Samba 4

ldapsearch -x -H ldap://127.0.0.1:389 \
  -D "CN=testuser,CN=Users,DC=corp,DC=local" \
  -w "User123456" \
  -b "DC=corp,DC=local" \
  "(sAMAccountName=testuser)"

-x：使用 Simple Authentication（简单凭据认证）。

-H：指定 LDAP/Samba 4 服务器地址和端口。

-D：要验证用户的完整 DN（Distinguished Name）。

-w：对应用户的密码。

-b：查询的根节点路径（Base DN）。

虽然日志里有一行 `[warning]` 看起来吓人，但这不仅不是错误，反而展示了 RabbitMQ LDAP 插件针对 Active Directory 的**智能回退（Fallback）容错机制**。

让我为你详细拆解这段“带域名登录”的特殊流程：

### 流程拆解与 Warning 解释

#### 1. 尝试 Search（属性查询失败）

```text
LDAP filling template "${username}" with ... "corp\testuser"
Searching for DN for corp\testuser, got back []

```

* **发生了什么**：你配置了 Search-then-Bind 模式（`dn_lookup_attribute = sAMAccountName`）。RabbitMQ 拿着 `corp\testuser` 整个字符串去 Samba 里查哪个用户的 `sAMAccountName` 叫这个名字。
* **为什么报 Warning（返回空）**：在 Samba/AD 的数据库里，`sAMAccountName` 的值仅仅是 `testuser`（不包含 `corp\` 前缀）。所以搜索结果返回空集（`got back []`），发出一条 Warning。

#### 2. 触发 AD 原生智能绑定（Bind 成功）

```text
LDAP bind succeeded: xxxx

```

* **发生了什么**：RabbitMQ 的 LDAP 插件极其聪明。它发现 Search 阶段找不到人，但因为输入格式包含反斜杠（`corp\testuser`），它意识到这可能是一个 AD 环境。于是它直接跳过了“寻找完整 DN”的过程，**将 `corp\testuser` 和你输入的密码直接发给 Samba 进行校验。**
* **结果**：Samba/AD 原生就支持识别 `DOMAIN\user` 这种 NetBIOS 登录格式。Samba 验证通过，返回了 `bind succeeded`。

#### 3. 标签授权与最终放行

```text
LDAP DECISION: does corp\testuser have tag management? true
LDAP DECISION: login for corp\testuser: ok

```

* **发生了什么**：认证通过后，RabbitMQ 读取你之前配置的常量规则（`{constant,true}`），为该次会话分配了管理标签。登录宣告成功。

---

### 结论

无论是纯用户名 `testuser` 还是带域前缀的 `corp\testuser`，这套配置利用了 RabbitMQ 插件的双层机制，做到了全兼容：

* **纯用户名** $\rightarrow$ 通过 Search 查出完整 DN $\rightarrow$ Bind 验证 $\rightarrow$ 成功。
* **带域前缀** $\rightarrow$ Search 失败报错 $\rightarrow$ 触发 AD 原生 Direct Bind $\rightarrow$ 成功。

这个 `[warning] <0.571.0> Searching for DN ... got back []` **完全可以无视**，这是为了实现两种格式兼容而必然产生的良性告警。如果你未来关闭了 `auth_ldap.log = false`，这条 Warning 就不会再出现了。
